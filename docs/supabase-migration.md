# Migrating to Supabase

Status of this change set, and what you need to do to run it.

## What is done (this PR)

**Phase 1 of 6: the database moves from SQLite to Supabase PostgreSQL.**

- `prisma/schema.prisma` targets `postgresql`, with a pooled `DATABASE_URL` for
  the app and a direct `DIRECT_URL` for migrations.
- The ten SQLite migrations are replaced by one PostgreSQL baseline,
  `prisma/migrations/00000000000000_init`. They could not be kept: they are
  SQLite DDL (`PRAGMA`, table-rebuild `ALTER`s) and will not run on Postgres.
  The baseline is generated from the same schema and produces an identical
  database — verified with `prisma migrate diff`, which reports no drift.
- `prisma/data-migration/{export,import}.ts` move the existing rows across.
- `.env.example` documents every variable the finished migration needs.

**Not done yet** — see "Remaining phases" below. This PR is infrastructure
only: no application code changed, and all 182 tests still pass.

## What you need to do

### 1. Get the database connection strings

Supabase dashboard → **Settings → Database → Connection string**.

You need two, and they are different on purpose:

| Variable | Port | Used by | Why |
| --- | --- | --- | --- |
| `DATABASE_URL` | 6543 | the app | Transaction pooler. Serverless functions open many short connections and Postgres does not cope well with that. |
| `DIRECT_URL` | 5432 | `prisma migrate` | Migrations need session state a transaction pooler does not provide. Pointing this at 6543 makes `migrate deploy` fail. |

Append `?pgbouncer=true&connection_limit=1` to `DATABASE_URL`.

### 2. Fill in `.env`

`NEXT_PUBLIC_SUPABASE_URL` and the publishable key are already set. Still
needed:

```
DATABASE_URL=...          # pooled, port 6543
DIRECT_URL=...            # direct, port 5432
SUPABASE_SERVICE_ROLE_KEY=...   # Settings -> API
```

The service-role key bypasses Row Level Security. It must never reach the
browser or the repository.

### 3. Create the schema

```bash
npx prisma migrate deploy
```

26 tables, 30 foreign keys, 27 indexes.

### 4. Move the existing data

The export has **already been run** against the old SQLite database and its
output is at `prisma/data-migration/snapshot.json` — 255 rows:

| | rows | | rows |
| --- | ---: | --- | ---: |
| exerciseAttempt | 99 | srsState | 7 |
| item | 38 | lessonProgress | 5 |
| itemConstruct | 40 | module | 5 |
| attempt | 20 | tier | 4 |
| construct | 13 | user | 2 |
| examSession | 10 | moduleSkillStatus | 2 |
| constructAccuracy | 7 | readingProgress | 2 |
| | | userProfile | 1 |

That file is **gitignored** — it contains real emails and password hashes — so
it exists only on the machine the export was run on. To load it:

```bash
npx tsx prisma/data-migration/import.ts            # first run
npx tsx prisma/data-migration/import.ts --upsert   # re-runnable, idempotent
```

Ids are preserved exactly. The cuids are portable, so every foreign key in the
snapshot still resolves without a remapping table, and nothing in this schema
uses a database sequence — every id is generated by the application — so there
are no sequences to reset afterwards.

If the snapshot is missing (fresh clone), regenerate it from a SQLite database
by checking out the previous commit's schema and running
`npx tsx prisma/data-migration/export.ts`.

### 5. Seed content, if starting empty

```bash
pnpm db:seed
```

Only needed on a database with no data. The import above already carries the
seeded content.

## Design decisions

### Prisma stays; Supabase provides the platform

The app has **97 query call sites across 34 files**. Rewriting them as
`supabase-js` calls is the rewrite this work was told not to do, and Prisma
targets Postgres natively — so the datasource swap is one line and every query
keeps working.

Supabase is therefore the database, the auth provider and the file store;
Prisma is the query layer and owns migrations. The two do not conflict:
`supabase-js` speaks HTTP to PostgREST, Prisma speaks the Postgres wire
protocol to the same database.

### Row Level Security is defence in depth, not the primary control

Prisma connects as the table owner, so **RLS does not apply to its queries**.
That is a real limitation and worth stating plainly rather than implying the
policies are doing work they are not.

It is acceptable here because the app has no browser→Supabase data access:
every read and write goes through a Next.js server route or server component
that already scopes by `userId`. RLS (Phase 5) will be enabled so that any
future direct client access — or a leaked publishable key — is contained, but
the server-side scoping remains the control that is actually enforcing
authorization today.

If RLS needs to be the primary control, the option is to connect Prisma as a
restricted role and `SET LOCAL request.jwt.claims` per transaction. That works
but wraps every call in a transaction; it was judged not worth the risk for
this change set.

### Enum-shaped columns stay as `text`

Several columns are enums in spirit — `status`, `skill`, `category`,
`examType` — and are stored as strings validated in `lib/constants.ts`. The
old schema comment anticipated promoting them to native Postgres enums.

They are deliberately **not** promoted here. It would change write semantics
(every insert must match the type exactly, and adding a value later needs its
own migration), and this change set's job is to move infrastructure without
altering behaviour. It is worth doing as its own PR, where the blast radius is
visible and testable on its own.

## Remaining phases

| Phase | Work |
| --- | --- |
| 2 | `lib/repositories/*` — a data-access seam so the 4 server components and 26 API routes stop calling the ORM directly |
| 3 | `lib/supabase/{client,server,admin}`, `@supabase/ssr` cookie sessions, Google OAuth, `/auth/callback`. `auth()` keeps its current signature so all 43 call sites are untouched |
| 4 | Vercel AI SDK: `lib/ai/registry.ts` with Anthropic and OpenAI, rewriting the 4 direct-SDK call sites to `generateObject`/`streamObject` with their existing Zod schemas |
| 5 | RLS policies |
| 6 | End-to-end verification against the live project |

Phase 4 has one complication worth flagging early: all four AI call sites use
Anthropic-specific options (`thinking: {type:"adaptive"}`, `output_config.effort`)
and one deliberately streams because a 64k-token pass would otherwise hit the
HTTP timeout. The provider abstraction has to pass those through for Anthropic
and degrade cleanly for OpenAI, rather than pretending the providers are
interchangeable.
